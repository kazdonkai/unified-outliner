# Changelog

This project follows [Semantic Versioning](https://semver.org/). The entries below begin with the first Git baseline created after Phase 4F.

## [Unreleased]

### Added

- Phase 5M-1 (create mirror): the Outline Tree's section, list item, standalone callout/blockquote/fenced-code/table and paragraph rows now have **Create mirror below** (sections: **Create mirror above**), and the Command Palette has **Create mirror: insert embed below cursor block** (the block at the cursor, resolved like Move block). It inserts a same-note Obsidian embed — `![[#Heading]]` for a section, `![[#^block-id]]` for a block — which, with "Show mirror embeds in Outline Tree" on, immediately shows as a read-only `⧉ Mirror:` row. A section's embed goes directly ABOVE its heading: every line below a heading (up to the next heading of the same or a higher level) belongs to that section, so an embed anywhere below it would embed the section inside itself. A block's embed goes directly after it; a list item's goes after its whole root list so the list is never split. Blocks without an id get one (`^uo-` + 8 lowercase alphanumerics) following Obsidian's conventions — at the end of a paragraph's / list item's own last text line, or on its own line after a blank line for a callout, blockquote, table or code block — and existing ids are reused; a new id is checked for uniqueness on the re-parsed result (regenerated on collision), and headings never get one. The id and the embed are one edit, applied through `applyLineEditOutcome`: one Undo step. Blank-line separation reuses Phase 5E-Copy's `ensureCopySeparation` (the D&D `ensureBlankSeparation` plus a blank line next to a list line). Creation is refused, with a Notice, when the new mirror would be circular (a self-reference, or closing a loop through existing mirrors) or when the insert would change any existing structure; a target that cannot be found or an ambiguous reference (duplicate heading text / id — the first match is used, as in Obsidian) only produces a warning. Resolution moved to the new pure module `src/mirror/resolveMirrorSource.ts` (re-exported from its Phase 5M-0 location) and now reports `matchCount`; cycles still come from Phase 5M-0's `detectMirrorCycle`. CompositeBlock rows, blocks nested in a list item, and mirror rows themselves get no Create mirror item; no new read-only exception path was added and the Phase 5E-Copy copy-pending state is untouched. See `docs/phase5m-1_mirror-create-design-memo.md` and the real-device checklist `docs/phase5m-1-verification.md` (not yet run — the developer's own responsibility).

## [0.8.0] - 2026-09-24

### Added

- Phase 5M-0 (mirror foundation): the first, display-only step of single-note mirrors. New pure modules under `src/mirror/` — `mirrorTypes.ts` (`MirrorKind` = `"heading" | "block-id"`, `MirrorSource`, `MirrorNode`, `MirrorResolutionResult`), `parseMirrorEmbed.ts` (a whole-line `![[#Heading]]` / `![[#Parent#Child]]` / `![[#^block-id]]` embed referring to the same note; another note's heading/block, whole-file embeds and anything else return null), `detectMirrorCycle.ts` (an embed whose target contains another embed — or itself — forms an edge; strongly-connected components mark circular embeds) and `scanMirrorEmbeds.ts` (recognizes such embed lines on top of the existing paragraph scan, without changing `parseDocument`/`scanComplexBlocks`, and resolves each to its heading's section or its block-id block). A new, off-by-default setting "Show mirror embeds in Outline Tree" projects each one as its own read-only `⧉ Mirror: <target>` row (a new `"mirror"` Tree node kind, in the read-only set, with no context menu, rename, drag and drop, Partial Edit or copy/paste entry point, and no fold identity); an unresolved or circular embed is flagged. Clicking the row (or Enter) jumps to the referenced heading/block. With the setting off, embed lines are handled exactly as before (as paragraphs), and while it is on an embed shown as a mirror row is not also listed as a paragraph row. No mirror editing or syncing yet, and no mirror database — the note's own embed syntax is the only source of truth. See `docs/phase5m-0_mirror-foundation-design-memo.md`.

## [0.7.9] - 2026-09-24

### Added

- Phase 5E-Copy: block copy in the Outline Tree. Every section, list item (with its whole subtree), standalone callout/blockquote/fenced-code/table and standalone paragraph row now has **Copy block** and **Duplicate below** in its context menu (long-press on mobile). Duplicate below inserts an independent copy directly after the block (after the whole subtree for a section/list item). Copy block enters a copy-pending state — shown as a banner above the Tree with a cancel button, and a dashed outline on the source row — after which every row offers **Paste block** (after), **Paste block above** (before) and, for section→section / list→list, **Paste block as child**; the state ends on a successful paste, Escape, the banner's cancel button, or **Cancel block copy**. The same four commands are in the Command Palette, acting on the minimal safe block at the cursor (the same resolution Move block uses). Placement reuses the existing Drag and Drop rules (`relocateSection`, `relocateListSubtree`, the standalone-complex-block drop resolver) and blank-line separation reuses `ensureBlankSeparation` unchanged, plus two copy-only additions (a blank line between a pasted callout/blockquote/code/table/paragraph and an adjacent list line, and after a pasted section's body before a following heading). The source is strictly read-only: a successful copy only ever inserts lines — no existing line, the original included, is rewritten (ordered lists are not renumbered). Pasting inside the source (onto its own descendant, or as its own child), inside a CompositeBlock, or inside frontmatter/a code block/a callout is refused with a Notice; the source and target are re-resolved against the current text at paste time (a changed source is refused rather than guessed at); and the result is re-parsed and refused unless every pre-existing section/list node, complex block and CompositeBlock survives unchanged apart from the line shift and the inserted segment is a faithful replica of the source. Every copy is written through the existing `applyLineEditOutcome` path — one `replaceRange`, one Undo step. Paste is limited to the note the block was copied from; CompositeBlock parents/members are paste targets but not copy sources in this phase. New pure module `src/edit/copyBlock.ts`; see `docs/phase5e-copy_block-copy-design-memo.md` for the design and `docs/phase5e-copy-verification.md` for the real-device (Mac/iPad) acceptance checklist, which has not yet been run and is the developer's own responsibility.

## [0.7.8] - 2026-09-24

### Added

- Drag and Drop for a standalone callout/blockquote/fenced-code/table row (`view/OutlineTreeView.ts`'s existing D&D wiring, `move/findStandaloneComplexBlockDropTarget.ts#resolveStandaloneComplexBlockDropTarget`, `edit/dropStandaloneComplexBlock.ts`) can now cross a section boundary — dropping one of these blocks relative to a target under a *different* heading (or between top-level and under-a-heading scope) is no longer refused. This lifts the resolver's own `target.parentId !== source.parentId` → `"not-same-section"` rejection entirely, following the exact same "cut the source's own line range and re-insert at the target-derived position, letting a fresh re-parse resolve the new `parentId` naturally — never write it by hand" approach `move/findMoveTarget.ts`'s own cross-section list-item move (`{ kind: "insert" }`) already established; no new insertion primitive was introduced (`move/moveBlock.ts#insertBlockAt` is reused unchanged). A drop that would land strictly inside a THIRD-PARTY CompositeBlock's own aggregate range in the destination section is still refused as `"composite-internal-boundary"`, exactly as it already was for a same-section drop — this guard already iterated every composite in the document regardless of section, so it needed no change at all to extend correctly. A cross-section drop now also gets `ensureBlankSeparation` (a blank line inserted on either side of the moved block when needed, folded into the same single edit/Undo step) so the relocated block can never silently merge with unrelated destination-section content that has no blank-line boundary. Section heading rows themselves are still never a drop target (out of this ticket's scope, as they already were) — a block dropped "before"/"after" a top-level block or list item in the destination section lands correctly without needing one. Move up/down's own cross-section support is a separate, not-yet-addressed follow-up ticket. `view/OutlineTreeView.ts`'s own drop-target-hint resolution needed no change at all — it already resolved a hovered row's target hint from any section, the restriction lived solely in the resolver. **[2026-09-25 追記, fix/standalone-dnd-blank-separation-always]** `ensureBlankSeparation` originally fired only for a cross-section drop — a same-section drop kept its exact prior byte-for-byte output, on the unverified assumption that every same-section drop target was already a blank-line-separated, safe position. A real-device (iPad) report showed that assumption was wrong: dropping a blockquote directly above an unrelated paragraph in the SAME section, with no blank line between them, silently merged the paragraph into the blockquote's own body on re-parse. This defect predates this cross-section ticket entirely (it goes back to Phase 5D-3C, the original callout/blockquote D&D implementation); the cross-section ticket's own same-section gate merely left it unprotected rather than introducing it. `ensureBlankSeparation` now applies unconditionally, on every drop, same-section and cross-section alike — matching `edit/paragraphNonAdjacentMove.ts#moveParagraphNonAdjacent`'s own unconditional posture. See `docs/feat_standalone-complex-dnd-cross-section-design-memo.md` for the full design, including its pre-investigation summary of how this differs from list cross-section Move, and its dated §8 addendum covering this follow-up fix.

- Paragraph Drag and Drop now supports cross-section (non-adjacent) moves, bringing it to parity with the standalone callout/blockquote/fenced-code/table D&D cross-section support above. `edit/paragraphNonAdjacentMove.ts#moveParagraphNonAdjacent` no longer rejects a target under a different section as `"parent-mismatch"`/`"depth-mismatch"` — it cuts the source paragraph and reinserts it at the target-derived position via the existing `insertBlockAt` primitive, letting re-parsing resolve the moved paragraph's new `parentId` naturally, exactly like the list and standalone-complex-block cross-section moves already do. `view/OutlineTreeView.ts`'s own D&D preview gate (`resolveParagraphNonAdjacentDragTarget`) was widened to match. A new `composite-internal-boundary` guard (new for this function, applying to both same-section and cross-section moves) rejects a drop that would land strictly inside an existing CompositeBlock's own aggregate range, mirroring the standalone-complex-block D&D resolver's identically-named check. The context-menu "move to top/bottom"/"move before/after a specific sibling" commands, and Move up/down for either paragraphs or complex blocks, are unchanged and remain same-section only — this is a D&D-only change. See `docs/feat_paragraph-dnd-cross-section-design-memo.md` for the full design; real-device verification has not yet happened and is the user's own responsibility.

- Phase 5E-3d: a standalone Markdown table block in the Outline Tree now has Move (up/down, swapping with the adjacent standalone sibling in the same section), Delete (removed as one atomic unit, header row through the final data row, with the same 3+-blank-line-to-2 normalization fenced-code delete already had), and Drag and Drop — bringing it to parity with fenced-code's existing Move/Delete, plus adding D&D for table specifically. This reuses the exact same kind-gated pipelines callout/blockquote/fenced-code already share (`moveStandaloneComplexBlock`, `deleteStandaloneComplexBlock`, `resolveStandaloneComplexBlockDropTarget`, and the Outline Tree's own drag-wiring guard) — no new range-determination logic and no parallel move/delete/drag pipeline was written; every kind allow-list was simply widened to also admit `"table"`. Conflict detection and blank-line policy around a moved/deleted table fall out of that same reuse, with no table-specific exception added. A table nested inside a list item's continuation, or one whose structure can't be confidently parsed, is safely excluded and refused exactly like it already was for fenced-code. Two same-branch follow-up fixes are folded into this same Unreleased entry rather than getting their own bullets: (1) standalone callout/blockquote/table rows now also get Drag and Drop on mobile/touch devices, via the same six-dot grip handle (`dragHandleEl`) the Outline Tree's list/section/composite rows already use — the original table D&D above only worked on desktop until this fix, a gap discovered during real-device (iPad) testing of this phase; and (2) fenced-code now also has Drag and Drop, on both desktop and mobile, closing the one remaining gap between fenced-code and callout/blockquote/table — fenced-code previously had Move/Delete/Partial Edit only (Phase 5E-1's original scope), and this was extended by explicit follow-up request once table's own D&D landed. Both follow-ups reuse the same kind-gated pipelines and drag-wiring guard as everything else in this entry — no new logic, only widened allow-lists. A third same-branch follow-up is folded in here too: standalone callout/blockquote rows now also have Delete, closing the one remaining gap between them and fenced-code/table (they already had Move up/down and Drag and Drop) — discovered during the user's own real-device (iPad) acceptance testing of this phase, not a technical limitation of the existing delete pipeline (`deleteStandaloneComplexBlock`'s own delete/re-verify/blank-line-normalization logic was already kind-generic), simply never requested for those two kinds until now; the same `StandaloneComplexBlockDeleteKind` allow-list, the Delete menu item's own kind gate, and `ConfirmFencedCodeDeleteModal`'s title selection were widened, with two new kind-neutral-body-reusing title keys (`modal.deleteCalloutTitle`/`modal.deleteBlockquoteTitle`, EN/JA). See `docs/phase5e3d_table-move-delete-dnd-design-memo.md` for the full design, including its dated addenda; real-device verification has not yet happened and is the user's own responsibility.

### Fixed

- Standalone callout/blockquote Move up/down was hidden whenever the adjacent content was a paragraph or a plain list item, even though the same block's drag-and-drop already accepted those as valid drop targets — a real-device-reported asymmetry between a working drag handle and a hidden Move menu item. `parser/compositeBlocks.ts#evaluateStandaloneComplexBlockMovability`'s adjacency check now resolves through a new `findAdjacentStandaloneMoveNeighbor` (alongside `move/findStandaloneComplexBlockMoveTarget.ts`'s own resolver), which accepts a standalone paragraph or a standalone (non-nested, non-composite-member) list item as a valid Move partner, matching `move/findStandaloneComplexBlockDropTarget.ts`'s own broader notion of adjacency. Section-boundary crossing remains refused, and a CompositeBlock's own members are still never absorbed into a swap. `findAdjacentStandaloneComplexBlock` itself, and every other Move/Delete condition, is unchanged. See `docs/fix_standalone-complex-move-adjacent-parity-design-memo.md` for the full investigation and design.
- A standalone paragraph row's Drag and Drop in the Outline Tree could not be triggered at all on mobile/touch devices (real-device iPad report), the same class of bug already fixed for standalone callout/blockquote/table rows earlier in this Unreleased section. Two causes, both in `renderNode` (`src/view/OutlineTreeView.ts`): a paragraph row is always `readOnly` (Phase 5T-2 design) and never `isComposite`/an eligible standalone complex-member kind, so `dragHandleEl`'s generation condition never matched it and no six-dot grip handle was ever created; and the paragraph-only drag-wiring branch itself was gated `&& !Platform.isMobile`, excluding mobile entirely (a deliberate desktop-only scope decision at the time Phase 5T-2 first shipped). Fix: widen `dragHandleEl`'s generation condition with a new `isParagraph` term, remove the branch's `!Platform.isMobile` exclusion, and apply the same mobile/desktop draggable-attribute split (handle vs. row) section/list, the composite-parent branch, and the standalone callout/blockquote/table/fenced-code bridge branch already use. The `dragstart`/`dragover`/`dragleave`/`drop`/`dragend` listeners needed no change (already platform-agnostic), and no CSS changes were needed. See `docs/fix_paragraph-mobile-drag-handle-design-memo.md` for the full design.

## [0.7.7] - 2026-09-24

### Added

- Phase 5E-3c: a lightweight Table Mode for the Partial Edit pane, built on Phase 5E-3b's `EditableMarkdownTable`/`parseMarkdownTable`/`serializeMarkdownTable` foundation. Opening a table block in Partial Edit now shows Raw and Table tabs above the shared editor (a fenced-code block still shows only its existing language-selector editor, with no Table tab). The Table tab renders each header and data cell as an inline-editable text field, per-column Left/Center/Right/None alignment toggles, row handles with move-up/move-down and delete controls, an "add row" button, per-column delete buttons, and an "add column" button — all as pure functions over `EditableMarkdownTable` (`src/edit/tableModeOperations.ts`), so Apply always routes through the existing `applySubtreeEdit`/`dispatchAndApply` write path with no new write path added. Switching Raw → Table re-parses the textarea's current text and refuses the switch (showing the failure reason) if it isn't a valid table; switching Table → Raw re-serializes first, so both tabs always reflect the same underlying edit. Deleting the last remaining row or column is refused with a Notice rather than silently emptying the table; moving the first row up or the last row down is a no-op with the corresponding button disabled, by design. Cell text is treated as plain text (no WYSIWYG rendering of inline Markdown), and the generated Markdown keeps the existing single-space cell padding — no column-width alignment/formatting. The alignment toggle buttons render as compact icons (with the full label as a tooltip) rather than translated text, avoiding label overflow/overlap at narrow column widths in Japanese. See `docs/phase5e3c_table-mode-design-memo.md` for the full design and real-device verification record (confirmed on the Method Vault Test note).

## [0.7.6] - 2026-09-24

### Added

- Phase 5E-3b: a new pure, Obsidian-free Markdown table parser/serializer (`EditableMarkdownTable`, `parseMarkdownTable`, `serializeMarkdownTable` in `src/edit/editableMarkdownTable.ts`), converting a Markdown pipe-table's raw text to and from a structured `{headers, alignments, rows}` shape with guaranteed round-trip stability in both directions. The parser splits table rows character-by-character rather than a naive pipe split, so a backslash-escaped pipe (`\|`) and a pipe inside a matched-length inline-code span are correctly excluded from the column split; a nested or mismatched-length code span is explicitly out of scope and rejected rather than guessed at. This phase adds no UI and does not touch the Partial Edit save path, conflict detection, the Outline Tree projection, or the range parser — it exists purely as the foundation Phase 5E-3c's Table Mode will be built on. ## [0.7.5] - 2026-09-23

### Added

- Phase 5E-3a: a new fenced code block or Markdown table can now be inserted directly below a section heading or a list item from the Outline Tree's right-click menu ("Insert code block below" / "Insert table below"), without leaving the Tree. Insertion is only offered where the resulting position is unambiguous — immediately under a section/root or right after a list item's own block, never inside a list item's own text or a composite/complex-member row — every other position shows the menu item as unavailable, and clicking it explains why via a Notice rather than silently doing nothing. A fenced code block is inserted via a language picker (Plain, Mermaid, Dataview, DataviewJS, JavaScript, TypeScript, Python, YAML, JSON, SQL, Shell, CSS, HTML, or a validated Custom… info string), reusing the same `CodeBlockPreset` registry the Partial Edit pane's own language selector already draws from; a table is inserted via a column-count dialog (1–8 columns) or a one-click minimal 2-column template. Either insertion opens the new block directly in the Partial Edit pane, and required blank-line padding is added without disturbing any existing blank lines elsewhere in the note. The insert and the pane's first Apply on that block are folded into a single Undo step, and the whole insertion is rejected — leaving the note byte-for-byte unchanged — if it would break an existing fenced-code pairing or a composite block's structure. Also fixes two real-device-reported issues found during this phase's own verification: the Partial Edit pane's empty-state placeholder text no longer leaks into a freshly loaded node, and — because fenced-code/table block ids are positional and can shift when an inserted block is undone in the note body — the pane now correctly shows an "unavailable" state instead of silently displaying an unrelated pre-existing block's content after such an Undo. See `docs/phase5e3a_structured-block-insert-design-memo.md` for the full design and real-device verification record.

## [0.7.2] - 2026-09-23

### Added

- Phase 5E-2A table raw Partial Edit with structural validation: building on Phase 5E-0's read-only Outline Tree projection and Phase 5E-1's fenced-code raw Partial Edit pattern, a standalone Markdown table can now be opened in the Partial Edit Pane as one raw-Markdown editable unit (the entire table, header row through the final data row). Apply validates the edited text is minimally valid table structure — at least 3 lines (header, delimiter, one or more data rows), every line containing at least one `|`, the delimiter row's cells all matching `:?-+:?`, and every row having the same column count (leading/trailing pipes normalized before comparing) — rejecting Apply and leaving the note unchanged on the first failed check, and reuses the existing conflict-detection mechanism unchanged. The `resolveInsertion` stub (`src/tree/insertionFramework.ts`) now also has a real implementation for `"table"` (both before/after positions); `"heading"`/`"list-item"` remain unimplemented stubs. ## [0.7.1] - 2026-09-23

### Added

- Phase 5E-1 fenced code block move, delete, and raw Partial Edit: building on Phase 5E-0's read-only Outline Tree projection, a standalone fenced code block (including Mermaid) can now be moved up/down to swap with its adjacent sibling (same parent only), deleted as one atomic unit (open fence through close fence, normalizing 3+ resulting blank lines down to 2), and opened in the existing Partial Edit Pane as one raw-Markdown editable unit (fence syntax included). Apply rejects an edit whose first line is not a valid opening fence or whose last line is not a valid closing fence (same fence character, at least as many marks, nothing else on the line), and reuses the existing conflict-detection mechanism unchanged. Markdown tables remain fully read-only, unchanged from Phase 5E-0 — none of table's own projection or read-only defenses were touched. Mermaid diagram rendering, Dataview/DataviewJS execution, and recursive outline parsing of a code block's own body remain out of scope. The `resolveInsertion` stub added in Phase 5E-0.5 (`src/tree/insertionFramework.ts`) now has a real implementation for `"fenced-code"`/`"fenced-code-mermaid"` (both before/after positions); `"table"`/`"heading"`/`"list-item"` remain unimplemented stubs. See `docs/phase5e1_fenced-code-partial-edit-move-delete-design-memo.md` for the full design, including two deliberate deviations from a literal reading of this phase's own brief: a new, narrowly fenced-code-scoped delete module (no prior standalone-block delete pipeline existed to "reuse"), and `collectReadOnlyOutlineNodeIds`'s kind-inclusion left unchanged (fenced-code stays in the read-only set exactly like callout/blockquote always have, reaching full Move/Delete/Partial-Edit capability via the same dedicated, non-generic context menu those kinds already use, rather than through exclusion from that set — which would have also silently unlocked generic drag-and-drop/rename behavior contradicting this phase's own same-parent-adjacent-only move constraint).
- Phase 5E-0.5 insertion framework type definitions and design memo: added `src/tree/insertionFramework.ts`, defining the `InsertableBlockKind`, `InsertionPosition`, `InsertionRequest`, and `InsertionResult` types and a `resolveInsertion` pure-function signature for a future common framework that will let a new fenced-code, Mermaid fenced-code, table, heading, or list-item block be inserted immediately before or after an existing fenced-code/table Outline Tree row. This phase adds only the type shapes, a design memo (`docs/phase5e0_5_insert-framework-design-memo.md`) documenting the intended insertion-point resolution, block-kind, and boundary-safety rules, and a stub implementation that always throws — no UI entry point (context menu or command), Vault write, or Editor update exists yet. Existing Phase 5E-0 fenced-code/table projection, its read-only guards, and cursor-sync behavior are unchanged.
- Outline Tree View: a standalone fenced code block (including Mermaid, Dataview, and DataviewJS code blocks) or Markdown table can now be shown as its own read-only row in the Outline Tree, reusing the existing complex-member Tree node kind already used for standalone callout/blockquote rows (no new node kind or `ComplexBlockKind` was introduced). This is gated behind two independent, off-by-default settings — "Show fenced code blocks in Outline Tree" and "Show tables in Outline Tree" — so existing notes and installs see no change in the Tree until a setting is explicitly turned on, and the two block kinds can be shown or hidden independently of each other. A projected row's label summarizes the block without executing or rendering it (`Mermaid: <first body line>` / `Dataview: ...` / `DataviewJS: ...` / `<language>: <first body line>` for other languages, or `Code block` when no language is set and/or the body is empty; `Table: <header column summary>` or a plain `Table` fallback when the header can't be safely summarized), and follows the existing document line order and parent-child placement rules (section, root, or list-item child) already used for other standalone complex blocks. Only a safely-bounded block (an unclosed fence, a malformed table, or an otherwise ambiguous block is excluded, consistent with existing scanner diagnostics) is projected. Clicking or tapping a row jumps the editor cursor to the block's opening fence line or table header line, and placing the cursor anywhere inside the block (including its closing fence or a table's delimiter/body rows) highlights the same Tree row. These new rows cannot be used to rename, move, delete, insert, indent/outdent, drag-and-drop, or open Partial Edit — they are read-only display only; existing operations on the block from outside the Tree (such as the body-side "Move block" command) are unaffected. Editing fenced-code/table content, inserting new blocks, cell editing, and a full Table Mode remain out of scope for this change and are tracked separately.

## [0.7.0] - 2026-09-22

### Added

- Partial Edit Pane: opening a CompositeBlock (`list + callout` or `list + blockquote`) now shows a structured editor when the list member and trailing callout/blockquote member can be cleanly separated, instead of only a single raw-Markdown textarea. The list member gets its own single-line input, and the trailing callout/blockquote member reuses the exact same prefix-free structured editor (title, type, fold marker, and body edited separately, with no `>` prefix shown) already used for a standalone callout/blockquote. Apply, Cancel, dirty tracking, and conflict detection remain unified across the whole CompositeBlock — there is still exactly one save operation, never a partial save of just the list row or just the callout/blockquote row. Any structure the split/projection can't handle (an unsupported trailing member, a nested callout/blockquote, a gap between members) falls back to the previous raw whole-block textarea, unchanged.
- Partial Edit Pane: within a CompositeBlock's structured editor, the list member's input now hides its Markdown list marker (`-`/`*`/`+`) too, showing only the item's text — mirroring the marker-free treatment the trailing callout/blockquote member already had. This only applies when the list member is a single, unsplit line recognized by the existing grouping rules; a list item spanning multiple lines or containing a nested list, a task-list checkbox (`- [ ]`), or an ordered marker (`1.`) still shows its full raw line, unaffected. On Apply, the original marker, the whitespace after it, and the item's indentation are always restored exactly. This only applies to a single-line leaf item with no nested child list and no continuation paragraph; an ordered item (`1.`), a task-list item (`- [ ]`), a multi-line item, an item with a child list, or an item with a continuation paragraph still shows its full raw line, unaffected. This reuses the same marker/body model already introduced for a CompositeBlock's list member, and connects to the existing list Partial Edit save, Cancel, and conflict-detection path unchanged.
- Partial Edit Pane: a standalone single-line task-list item (`- [ ] ...` / `- [x] ...`) can now also be edited without typing its Markdown list marker or `[ ]`/`[x]` checkbox syntax — the editor shows just the item's own text, with a small checkbox control next to it for the completion state. This only applies to a single-line leaf task item (same scope as the non-task marker-free editing above: no nested child list, no continuation paragraph); an ordered item, a multi-line item, a CompositeBlock task-list member, or a checkbox status other than unchecked/checked still shows its full raw line, unaffected.
- Partial Edit Pane: a standalone single-line ORDERED list item (`1.`/`12.`/`1)`/`12)`, at any indentation) can now also be edited without typing its Markdown number marker — the editor shows just the item's own text, with a small text field next to it for the item's number. The number field validates strictly (a positive whole number only — an empty value, zero, a negative number, a decimal, exponential notation, or a value with surrounding whitespace are all rejected, with both the number and text drafts preserved) rather than relying on browser input behavior alone. Duplicate, non-sequential, or reverse-order numbers among sibling items are never a reason Apply is rejected — this pane never renumbers sibling items automatically. This only applies to a single-line leaf ordered item (same scope as the other marker-free editing above: no nested child list, no continuation paragraph); a task-list item, a multi-line item, or a CompositeBlock ordered-list member still shows its full raw line, unaffected.

The preview rows themselves remain fully read-only — clicking one never toggles its checkbox, edits its number or text, or lets it be dragged — this is a navigation shortcut only, never a second way to edit a child's content. Each click re-checks the target against the note's current content immediately beforehand, so a child that was deleted, moved, or edited elsewhere since the preview was last shown is never opened by mistake; the pane simply shows a notice and stays exactly where it was, with any unsaved parent edit left untouched.

This is a completely separate action from clicking the row itself, which still only navigates, unchanged. While a child is open this way, Apply saves the parent's own text and the child's text together, in one save — whichever of the two (or both) actually changed — so there is never a moment where only one of them is written to the note. Switching to a different eligible child, or closing the inline editor, while there are unsaved changes goes through the same Apply/Discard/Cancel dialog every other target switch in this pane already uses. A child that has grandchildren of its own, or whose content can't be safely marker-free edited (for example a continuation line containing a callout or code block), never shows the pencil icon — opening it for editing still requires navigating to it as its own pane, unchanged.

A child that isn't itself eligible for the inline editing above (one with grandchildren of its own, or unsafe to marker-free edit) likewise can't be marked for deletion — its row simply has no trash icon.

- Partial Edit Pane: a parent list item's read-only child preview now also lets you indent a direct child leaf into its immediately preceding sibling (as that sibling's new last child), and outdent a child nested exactly one level deep back out to a direct child of the same parent, positioned right after its former parent -- without leaving the pane. Eligible rows (a 2nd-or-later direct child for indent; any one-level-deep leaf for outdent) show a small indent/outdent icon; activating one decides the transformation immediately, and the preview shows the resulting hierarchy right away, before Apply -- the note's Markdown is never touched until Apply is pressed. ## [0.3.1] - 2026-08-11

### Added

- Added sibling previous/next navigation to the Partial Edit Pane header (docs/phase5b_sibling-navigation-spec.md), alongside the existing ancestor breadcrumb and Subtree Navigator. Two buttons let you move sideways to the loaded node's previous/next sibling — a section or list item sharing the same parent — without leaving the pane, including in a popped-out window. Each button disables itself when there is no sibling in that direction, and the destination's label is shown on hover. Navigation reuses the pane's existing guarded projection entry point, so unapplied edits are always confirmed (Apply / Discard / Cancel) before switching, exactly like breadcrumb and Subtree Navigator clicks already do.

## [0.2.3] - 2026-08-11

### Fixed

- Fixed the Outline Tree View's double-click-to-rename often failing to trigger. The double-click listener lived only on a row's text label, which is only as wide as its own text — double-clicking the empty space elsewhere in the row (common for short labels) missed it entirely. Double-click now starts a rename from anywhere on the row, except the fold/disclosure triangle, which keeps its own toggle-fold behavior.

## [0.2.2] - 2026-08-11

### Fixed

- Fixed the Outline Tree View's inline rename discarding an edit without any warning whenever focus left the input by any means other than pressing Enter — including simply clicking a different row to look at it. Moving focus out of the rename box now commits the edit (matching Finder/Explorer/VS Code tree-view conventions) unless the text was left completely unchanged, in which case it still cleanly cancels. Escape continues to always cancel explicitly.
- Fixed a related latent bug where committing an inline rename with the text left exactly as it started could insert a spurious blank line at the end of the note.

## [0.2.1] - 2026-08-11

### Fixed

- Fixed the Outline Tree View's long-press context menu on mobile (iPadOS/mobile Safari) sometimes failing to open, with a duplicated or corrupted pane appearing instead. Rows were marked `draggable="true"` even on mobile, where WebKit's native drag-lift gesture for touch-and-hold competed with the plugin's own long-press timer for the same gesture. Rows are now only marked draggable on desktop; mobile reordering was already available via the long-press menu's Move up/down and Indent/Outdent commands.

## [0.2.0] - 2026-08-11

### Added

- Added `Move section up` / `Move section down` commands that always move the whole enclosing heading section, regardless of where the cursor sits inside it.
- Redefined `Move block up` / `Move block down` to operate on the minimal safe unit at the cursor: a heading section, a list subtree, a plain paragraph, or — when the cursor is inside one — a whole callout, blockquote, fenced code block, or table. Ambiguous or unrecognized boundaries are rejected without editing the note.
- Added `Delete block (section / list subtree)`, `Insert sibling after current block`, and `Insert child list item` commands, wired into the Outline Tree View's context menu.
- Added inline rename for section headings and list items directly in the Outline Tree View: double-click a row (or press F2, or choose Rename from its context menu) to edit its text in place, with commit on Enter and cancel on Escape. Renaming is IME-safe, writes back through the plugin's normal safe edit path, and commits as a single Undo/Redo step. A newly inserted block is renamed automatically.
- Added mobile tap and long-press support in the Outline Tree View: a single tap selects a row, tapping an already-selected row starts inline rename, and a long-press opens the context menu.
- Added optional visual aids to the Outline Tree View: a subtle always-on background or left-edge stripe to distinguish section rows from list rows, a brief flash highlight on the row a `Move block` / `Move section` command just moved, and a short notice naming what was moved. All configurable under the new "Move & Outline Tree kind highlight" settings group (`Section background style in Outline Tree`, `List row highlight style in Outline Tree`, `Preview move target in Outline Tree`, `Show move result toast`).
- Added ancestor breadcrumb navigation and a Subtree Navigator to the Partial Edit Pane, for moving up to a parent or into a child block without leaving the pane.
- Added pop-out window support for the Partial Edit Pane, reachable from the Outline Tree View's node context menu.

### Changed

- User-facing text assembled by the plugin (notices, the move-result toast, and the Outline Tree View / Partial Edit Pane empty-state messages) now defaults to English, since the plugin is not limited to a specific language. This affects wording only, not behavior.
- The Partial Edit Pane now shows its Apply/Cancel controls only while there are unsaved changes, and its close button behaves consistently with that dirty state.

### Fixed

- Fixed the inline rename input in the Outline Tree View collapsing to a narrow width instead of filling the row.
