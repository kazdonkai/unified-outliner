# Phase 5E-3M（Mermaid 構造化部分編集）設計メモ

状態：**完了**（2026-11-13 ユーザーが Mac と iPad で実機受入の全20項目 Pass を確認。1.2.0 としてリリース）。ブランチ `feature/mermaid-structured-edit`、基点 `e8c3844`＝`fix/heading-adjacent-fenced-code`。

## 1. 目的と原則

Mermaid のコードブロックを、部分編集ペインの中で「前置き（設定）」「図の種類の宣言」「図の本文」の三つに分けて表示し、図の種類をプルダウンで選び、本文だけを編集欄で直せるようにする。利用者がフェンスや図種のキーワードを入力しなくても、図の中身に集中できることが目的である。

Markdown を唯一の正とする。構造化した状態は画面の上だけのものであり、Apply で書き込まれるのは常に、元の Mermaid コードブロックの本文を組み立て直した一つの文字列である。書き戻しは既存の `applySubtreeEdit` の経路をそのまま使う。

### ロードマップとの関係

`docs/phase5e_fenced-code-and-table-roadmap.md` §4.1・§4.2 は、コードブロックの編集を「種別選択＋平文編集」にとどめ、Mermaid 専用の GUI を対象外としていた。Phase 5E-3M はこの方針を一段だけ広げる。

| 区分 | 扱い |
|---|---|
| 今回含めるもの | 図種の宣言の分離と選択、新規作成時の雛形 |
| 引き続き対象外 | ノードやエッジのフォーム編集、構文の完全な検証、プレビューの描画、図種の自動変換 |

## 2. 前提として行った変更：フェンス行の原文保持（§1-1）

構造化編集は「何も変えずに Apply すれば一字も変わらない」ことを前提にする。そこで、`applySubtreeEdit` の fenced-code 分岐を次のように改めた。

- info string が抽出時点から変わっていない場合は、元の開始フェンス行と閉じフェンス行をそのまま使う。`` ```mermaid `` が `` ``` mermaid `` になる現象はなくなった。
- info string を変えた場合に限り、開始行を従来どおり `indent + フェンス + " " + info string` で組み立て直す。閉じ行は info string を持たないため、原文を保つ。
- 原文の行が既存の検証に通らない場合だけ、合成した行へ戻す（防御的措置）。
- 本文中に、このブロックを途中で閉じてしまう行があれば、新しい理由 `fenced-code-premature-close` で Apply を拒否する。判定にはパーサ（`parseDocument` の `FENCE_RE`）と同じ規則を使う。すなわち、行頭の空白の後に同じフェンス文字が3個以上続く行は、長さや後続の文字に関係なく拒否する。CommonMark より厳しいが、以後このノートを読むのはこのパーサだからである。

Phase 5E-3 設計メモの「副作用：空白の正規化」の節に追記した。

## 3. 分解の規則（`src/edit/mermaidStructure.ts`）

入力はコードブロックの本文（フェンス行を除く）である。`"\n"` で分割するので、CRLF の `\r` は各行の末尾に残り、そのまま保たれる（`parseDocument` と同じ扱い）。`mermaid.detectType()` は原文の位置を返さないため使わない。

1. 全体が空白だけなら `empty` とする。
2. 上から読み、空行と `%%` で始まる行（コメント）は前置きに入れる。
3. `%%{` で始まる行は、`}%%` を含む行（同じ行でもよい）までを一続きのディレクティブとして前置きに入れる。閉じなければ `unclosed-directive` とする。
4. 前置きの中で最初の、空行でもコメントでもない行が `---` であれば frontmatter とみなし、次の `---` 行までを前置きに入れる。閉じなければ `unclosed-frontmatter` とする。frontmatter は一度だけ認める。
5. 前置きの後で最初の、空行でもコメントでもない行を宣言行とする。行が無ければ `no-declaration` とする。
6. 宣言行は「先頭の空白（indent）＋最初の空白でない語（keyword）＋残り（suffix）」に分ける。この分割は必ず元に戻せる。keyword が登録表と一致しなければ `unknown-diagram` とする。一致の判定は大文字と小文字を区別する。
7. suffix が図種の方針に合わなければ `unsupported-suffix` とする（例：`graph TD; A-->B`、`mindmap root`）。
8. 宣言行より後の行は、すべてそのまま本文とする。

組み立て直しは「前置き＋宣言行＋本文」を `"\n"` でつなぐ。宣言行は、indent・keyword・suffix がどれも元のままなら `rawLine` をそのまま使い、どれかが変わった時だけ組み立てる。

### 守るべき性質（`tests/mermaidStructure.test.ts`）

1. 分解に成功したブロックは、何も変えずに組み立て直すと元の文字列と一字一句同じになる。
2. `graph` と `flowchart`、`stateDiagram` と `stateDiagram-v2` の表記は、利用者が図種を選び直さない限り変えない。方向の `TB` と `TD` も同様である。
3. 分解に失敗したブロックは書き換えない（ソース表示になる）。

## 4. 図種の登録表（`src/edit/mermaidDiagramTypes.ts`）

指示書の表のとおり、flowchart・sequence・class・state・er・gantt・pie・mindmap・timeline・journey・gitgraph の11種を登録した。図種を増やす時は、この表に1項目を足し、i18n に表示名を2つ（日本語と英語）足すだけでよい。

| suffix の方針 | 図種 | 構造化表示での扱い |
|---|---|---|
| `direction` | flowchart | 方向プルダウン（指定なし／上から下／下から上／左から右／右から左）。`TB` と `TD` はどちらも「上から下」と表示し、選び直さない限り原文の表記を保つ |
| `empty` | sequence ほか | suffix は空白だけを認める |
| `raw` | pie・gitgraph | 小さな入力欄で、原文の suffix（前後の空白を除いた部分）を編集する |

図種を選び直した時は、登録表の先頭のキーワード（`flowchart`、`stateDiagram-v2` など）と既定の suffix（flowchart は ` TD`）を書く。行末の空白（CRLF の `\r` を含む）は保つ。読み込んだ時の図種を選び直した場合は、読み込んだ時の宣言行をそのまま戻す（`graph TD` → mindmap → flowchart と操作すると `graph TD` に戻る）。

### 雛形

各図種に、本文の部分だけの最小の雛形を持たせた（マインドマップは中心と枝2つ、フローチャートはノード2つと線1本、シーケンス図は登場者2人とメッセージ1つ、他も同程度）。雛形を使うのは次の二つの場合だけである。

1. 新規作成時：`CodeBlockPresetModal` で Mermaid を選ぶと「図の種類」の段が現れる。図種を選べば宣言行と雛形を、「選ばない（既定）」なら従来の `bodyTemplate`（`flowchart TD` と空行）を挿入する。
2. 部分編集で、本文が空（空白だけの行を含む）の時に図種を選んだ場合。

本文がある時は、どんな操作をしても雛形で上書きしない。

## 5. 部分編集ペインの UI（`src/view/PartialEditView.ts`）

状態の遷移は `src/edit/mermaidStructuredSession.ts` の純粋関数にまとめ、View は DOM の操作だけを受け持つ。言語が `mermaid`（`isMermaidInfoString`）の時だけ、言語の行の下に Mermaid の行を出す。それ以外のブロックや種別では、Mermaid の行は常に隠れており、表示は従来のままである。

1. 「構造化」「ソース」の切り替え。独自スタイルの一体型スイッチで、選ばれている側だけをアクセント色で塗り太字にし、`aria-pressed` も付ける。テーマのボタン規則に負けないよう、Mermaid 行の下に限定した詳細度の高いセレクタで定義した（`!important` は使わない）。
2. 構造化表示では、図の種類のプルダウン（「マインドマップ（mindmap）」のように、表示名とキーワードを並べる）と、図種に応じた方向プルダウンまたは suffix 入力欄を出す。
3. 前置きに中身がある時だけ「図の設定あり（N行）— 編集はソース表示で行う」という折りたたみを出す。中は読み取り専用である。
4. 本文の編集欄には本文の行だけを出す。既存の textarea を再利用しているので、リサイズなどの機能はそのまま使える。
5. 構造化からソースへ切り替えると、組み立て直した全文が編集欄に入る。ソースから構造化へ切り替えると、編集欄の現在の文字列を分解し直す。失敗した時はソース表示のまま、理由を Notice で知らせる。どちらの向きでも未保存の編集は失われない。
6. 読み込んだ時点で分解に失敗したブロックはソース表示で開き、「ソースで編集します：この図の種類には未対応のため」のような短い理由を出す。

### 図種を変えた時（§1-6）

- 本文がある時は宣言行だけを置き換え、本文には手を付けない。直後に「図の種類だけを変えました。本文は自動では変換されません。新しい図の種類に合わせて本文を直してください。」と表示する。「変換」を思わせるボタンや操作は設けていない。
- Cancel は info string の選択と Mermaid の状態を読み込み時に戻し、元の宣言と本文を表示し直す。
- 言語を `mermaid` から別の言語に変えると、その時点の状態を組み立て直した全文を本文として編集欄に入れ、普通のコードブロックとして扱う。逆に、別の言語から `mermaid` に変えると、編集欄の現在の文字列の分解を試みる。

### Apply・汚れ判定・競合（§1-7）

- Apply は `mermaidFullText`（前置き＋宣言＋本文）を既存の `applySubtreeEdit` に渡す。競合の検出、ソースノートの rename・delete の追跡、stale の時に Apply を止める仕組みは、手を加えずにそのまま効く。
- 構造化表示の汚れ判定は「組み立て直した文字列が元の文字列と違うか」で決める。プルダウンを元の値に戻しただけなら汚れていない。
- 外部の変更で自動再読み込み（Phase 5L-12）が起きた時は、新しい本文から Mermaid の状態を作り直す。

## 6. 判断に迷った点と決定

| 論点 | 決定と理由 |
|---|---|
| 宣言行の後ろに `;` がある場合（`graph TD;`） | 方向として扱わず `unsupported-suffix` とし、ソース表示で編集させる。安全側の判断である。Minji の実データには存在しなかった |
| 本文中のフェンスらしき行の判定 | パーサの `FENCE_RE` に合わせ、CommonMark より厳しく判定した（§2） |
| 新しく flowchart を選んだ時の方向 | 既定の suffix を ` TD` とした。Obsidian の既存の新規テンプレート（`flowchart TD`）と同じである |
| raw suffix の編集欄に出す文字列 | 前後の空白を除いて出し、書き戻す時に元の区切りの空白と行末の空白を補う |
| Cancel で言語の選択も戻すか | 戻す（Mermaid 以外のコードブロックでも同じ）。Cancel は「読み込み時に戻す」操作だからである。Apply の結果には影響しない |
| 汚れ判定を `isDirty` のどこに入れるか | 既存の配線テストが論理和の並び順を固定しているため、Block ID の判定と同じく早期 return として加えた |

## 7. 範囲の外に置いたもの
